Hadoop · MapReduce
COMP30261 · Coursework 1 2025

Five-Node Hadoop Cluster & MapReduce Pipeline

Designed, installed, and operated a multi-node Hadoop cluster to process the 2018 UK Road Safety dataset (160,597 casualty records) using a custom Java MapReduce job. Traditional single-node RDBMS hits memory and I/O limits at this scale; the cluster used HDFS block replication, YARN resource management, and Spark alongside MapReduce.

What I built: Master node machine01 ran NameNode and ResourceManager; workers machine02–machine05 ran DataNodes and NodeManagers. Passwordless SSH, static IPs, and Hadoop XML config (core-site.xml, hdfs-site.xml, yarn-site.xml, mapred-site.xml) were cloned and tuned across the cluster, then validated with jps, HDFS CLI, and the NameNode / ResourceManager web UIs.

  • Stack: OpenJDK 8, Hadoop 3.3.6, Apache Spark 3.5.4 (standalone), Linux VMs, replication factor 3.
  • Job: RoadSafetyMapper / RoadSafetyReducer / RoadSafetyDriver packaged as CasualtyCount.jar, parsed CSV severity (column 8) and aggregated fatal / serious / slight counts.
  • Runtime: ~45 seconds with four map tasks and one reducer; YARN allocated 2GB per NodeManager and 1.5GB per mapper/reducer.
  • Critique: The ~52MB file fitted a single 128MB HDFS block, so true data-locality parallelism was limited; I documented that Spark in-memory processing and larger multi-block datasets would show stronger scale-out.

CAP · Architecture
COMP30261 · Coursework 2 2026

Distributed Database Architecture: CAP Trade-offs

Technical report comparing MySQL, MongoDB, Apache Cassandra, and HBase for two production scenarios. Recommendations were grounded in my Hadoop lab: NameNode heartbeats every 2 seconds showed why master-coordinated systems create a single point of failure, and Hive/MapReduce schema locks showed why rigid “schema-on-write” fails for evolving document data.

  • Scenario A, global messaging (billions of JSON messages/day): Chose Apache Cassandra. Need is AP (availability + partition tolerance) with eventual consistency. Cassandra is masterless, uses LSM trees for O(1) append-only writes (~850,000+ writes/sec vs ~12,300 on MySQL in my comparison), hinted handoff, and tunable consistency (CL=ONE). Future work I noted: Time Window Compaction (TWCS) for chat logs and token-aware drivers for cross-datacentre latency.
  • Scenario C, medical imaging & IoMT feeds: Chose MongoDB. Need is CP (strong consistency) for patient safety, GDPR Article 17, and NHS DSPT. Document model + dynamic schema handles JSON wearables, clinician notes, and new device fields without downtime; GridFS stores DICOM MRI/CT files with metadata in one queryable store. Lab evidence: joining nested JSON in MapReduce took 8+ minutes on 10GB, too slow for a clinical record.
  • Rejected options: MySQL (vertical scale, ACID lock contention); HBase (HMaster SPOF, weak nested-document queries); Cassandra for healthcare (stale telemetry is clinically unsafe); MongoDB for global chat (CP replica-set elections add 10–20s downtime).
